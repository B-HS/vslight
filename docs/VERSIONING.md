# 버전 정책

## 1. 규칙

버전 번호와 빌드 번호에 숫자 `4`를 절대 포함하지 않는다.

- `MARKETING_VERSION` (예: `0.1.0`)
- `CURRENT_PROJECT_VERSION` (예: `1`, `2`, `3`, `5`, ...)
- Git 태그 (예: `v0.1.0`)
- GitHub Release 제목과 본문의 버전 표기

## 2. 다음 버전 계산

`VersionPolicy`는 같은 규칙을 코드로 구현한다.

| 현재 | 다음 minor | 다음 patch |
| --- | --- | --- |
| `0.1.0` | `0.2.0` | `0.1.2` |
| `0.3.0` | `0.5.0` | `0.3.2` |
| `0.13.0` | `0.15.0` | `0.13.2` |
| `3.39.0` | `3.50.0` | `3.39.2` |
| `1.3.13` | `1.5.0` | `1.3.15` |

patch가 `3` 다음이면 `4`를 건너뛰고 `5`로 간다. minor가 `39` 다음이면 `40`부터 `49`까지 모두 금지되므로 `50`으로 간다.

## 3. 릴리스 절차

1. `project.yml`의 `MARKETING_VERSION`과 `CURRENT_PROJECT_VERSION`을 올린다.
2. `bash Scripts/check-version.sh`를 실행해 4가 없는지 확인한다.
3. 테스트를 실행한다.
4. Release 빌드를 만들고 Developer ID로 서명한다.
5. 공증(`notarytool submit --wait`)과 `stapler`를 수행한다.
6. Git 태그와 GitHub Release를 만든다. 이때도 버전 문자열에 4가 없는지 다시 확인한다.
7. 릴리스 노트에는 변경 사항과 알려진 제한을 적는다.

GitHub Actions 워크플로는 사용자가 제공하는 서명/공증 값이 준비된 뒤 별도 단계에서 추가한다.

## 4. 초기 릴리스 사다리

```text
0.1.0  첫 draft
0.2.0  출력 장치 데이터 소스, 안정성 개선
0.3.0  앱별 볼륨 조사 결과 반영
0.5.0  가상 드라이버 프리뷰
0.6.0  드라이버 설치 흐름
0.7.0  안정화
0.8.0  성능과 접근성
0.9.0  릴리스 후보
1.0.0  정식
```

`0.4.0`은 사용하지 않는다.

## 5. 검사 스크립트

```bash
bash Scripts/check-version.sh
```

`project.yml`에서 버전을 읽어 `4`가 있으면 exit 1로 실패한다. CI를 붙일 때 같은 스크립트를 첫 단계에 넣는다.
